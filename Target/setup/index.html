The governance trio

log / logFile - the durable ledger file (EACH plugin keeps its own, separate by default)

mutationTools - which actor tools count as triggers - the deployed layers set [write, edit, str_replace_editor, raw-write]

exclude - the exclusion segments - the plugin's own fence (node_modules, .git, .dsh, ...)

updateCooldownMs / maxUpdateFailures - the update stage's pacing and its circuit breaker (3 failures pause a directory)

updateMode + ncuBin / cargoBin - programmatic (library) vs bin (external binary via the subprocess seam); absolute paths because host PATH != shell PATH

strict - strip unknown dependencies - explicit ONLY, NEVER a default-delete

policyFile / keepFile / sections - the update-policy and keep-list sidecars, and which dependency sections the pinner touches

The stream flavors

log / logFile - the flavor's own ledger, separate from the family's logs

replacement - the transform's ONLY knob on class flavors (dash - / ellipsis ... / spaces space / invisible empty) - hot-editable, the next stream picks it up with NO remount

normalizeReasoning - default ON - normalize reasoning deltas and the assembled reasoning block too

normalizeToolArguments - default OFF - tool-call arguments are execution-critical raw JSON; the example patch turns it on (opt-in)

The file tool

log / logFile - the normalize-file ledger

replacement - the dash step's replacement - the transform's ONLY knob

normalize (per call) - the raw-write tool's sibling flag: absent/false = verbatim, true = ALL six transforms, or the flavor-name array

The guardians

ccr: thresholdBytes / previewMaxChars / multipliers - the compression gate's volatile knobs - hot-editable; targets/exempt/the store are structural (remount on edit)

ccr: autoExpand / compressFailures / journalPath - auto-expand on by default (small results stored and returned FULL); failures pass through; the store is memory-only until journalPath is set

coach: threshold / window / cooldown - 3 strikes within an 8-judged-call window, 10 calls between notes - EVERY cell volatile

coach: escalateThreshold / cleanWindow / enforce - the persistent section at 6, cleared after 12 clean calls; the deny tier off by default (enforce: 'off')

coach: judgeTools / fetchLive / maxSectionTools / sectionTtl - the judged tools (bash, pwsh), the live ctx.tools.schemas() fetch, the 8-row section table, the 20-call section cache

Optional by default

WHAT STAYS OFF UNLESS YOU ASK

The schema default OFF for tool-call arguments - execution-critical raw JSON - and the structural pass-through exemptions (edit/raw-write/normalize-file by identity, the __normalize:false first-key marker) when a patch turns it on.

normalizeToolArguments: false

DEFAULT OFF

The default.

Tool-call arguments are execution-critical raw JSON. Rewriting them is the user's accepted risk. The schema default is OFF and the example patch turns it on.

Effective tool-input normalization is normalizeToolArguments || scopes.toolInput. The field is kept and OR-ed in, so this knob and the granular scopes compose.

Even when on, the three structural exemptions pass through by identity - edit (its old_string must match the real file bytes), raw-write (it owns its content normalization through its explicit normalize parameter) and normalize-file (its arguments carry a file path). And a {"__normalize":false}-marked call passes through unnormalized: the per-call "leave that search alone" control. Its marker must be the FIRST key (the core strips the marker entry, so the executed call carries NO unknown key; a first delta shorter than the marker is invisible to the probe and the call normalizes normally).

SILENCE AS INVARIANT

Storage records buffer or drop when NO storage facility is present (the human ledger stays the complete record). Excluded paths log ONE line and move on. A no-op write writes nothing. A thrown-away stream writes NO ledger line.

Silence is the invariant. The ledger is the receipt.

The granular volatile scopes' defaults are exactly the pre-scopes behavior: conversation and reasoning on, toolInput / toolResults / batch off, files on - the whole object one volatile cell, so a flip lands on the next judged call with no remount.

OPT-IN

Pitfalls

THE KNOWN GAPS

The gaps and the working lessons, stated as they are.

The narrative form lives on the case-study page; this section is the setup-relevant inventory.

Pitfall What actually happens The lesson
Load order is not list order The pinner can activate before the governor at boot - the registration order is not controlled. Never rely on the bundles-list order for step ordering; the fold and the fresh-version writes make the order irrelevant. Each ledger answers for its own plugin.
The verifyCommand trap An update-policy verifyCommand can fail with a non-zero status - on a vendored-fork workspace, pnpm install has no registry to install from. The documented cordis registry trap: the failure is expected, not a bug. Exit 127 (the runner unavailable) is non-fatal; any other failure trips the circuit breaker (maxUpdateFailures).
The smoke/live fidelity gap All 1008 + 1021 smokes green does not prove the profile wiring - every real bug was found live, not by the smokes. The smokes prove the mechanics; the live battery proves the wiring. Verify the ledgers after every restart.
The timestamp confusion The ledger lines are ISO UTC; the storage records are epoch milliseconds; the local display adds +03. The "missing records" scares were filter mistakes, not lost data - check the timezone before hunting for loss.
The byte-integrity law A write that emits bytes the file's format forbids corrupts the file - the NUL-byte incident class, the lesson of the URL-registry corruption. Verbatim is the default; the normalize family restores the integrity; the byte-scan is the arbiter.
The raw-write marker semantics govern absent = no chain (the escape hatch); a marked call passes through only when marked. Markers are stripped before the tool validates - the harness tools reject unknown argument keys ( additionalProperties: false).
update: running verifyCommand: pnpm install update: verifyCommand failed (status 1) update: verifyCommand runner unavailable (exit 127) — skipped, non-fatal update stage FAILED (1) for <dir>; consecutive=2

The verifyCommand lines above are byte-exact ledger strings of the update stage's Verify step; the live battery's governed-chain fixture records the running and failure lines, and the smokes assert all four forms.
