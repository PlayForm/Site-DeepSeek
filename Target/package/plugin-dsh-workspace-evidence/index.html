servicectx.workspaceEvidencectx.workspaceEvidence - validate(id, kind, subject, dependencies, verdict?) records one validation object, check(id) reads its status, invalidate(key) is the explicit Acar seam, and list(status?) and statistics() report.
servicefour kindsof truth (the Representation-First research): reality, observation, representation, intent - different truth claims, different proof. The service owns the taxonomy and validates the kind at the call boundary.
listenerinvalidate(key)evidence dependencies: every validation object declares its dependencies; when a dependency changes (an fs/observed event through the factory's Wire, or an explicit invalidate(key)), every dependent object goes stale in one pass (the incremental-computation principle - the Acar seam). A stale object is never guessed back to fresh, because a revalidation is a new validation object, superseding the old. A repeat event (the same path carrying the same version within the coalescing window) runs no pass and records no line, because that file state's invalidation already ran (the version token identifies the state). The guard (Function/Duplicate, the monitor's clock pattern - no timer, 2 s, the State.Now test seam overrides it) is on the listener only, and the explicit invalidate(key) calls are never coalesced.
servicehonesty rule:the service records the caller's verdict and never invents one. The sequence is the service's own monotonic counter, never a wall clock.

Architecture

This plugin's own structure: the shape the portrait gives it, the facts its source documents, and the rule its flow obeys.

Shape

Plugs into the ctx.workspaceEvidence service, the fs/observed listener through the factory's Wire, and the storage domain.

The validation objects, and the invalidation pass that keeps them honest.

  • One validation with its kind, subject, dependencies, and verdict
  • Every dependent marked stale in one pass
  • A stale object never guessed back to fresh
  • A repeat event dropped silently, on the version token
Service ctx.workspaceEvidence
5 Methods
3 Consumers
Methods
  1. validate record one validation with its kind, subject, dependencies, and the caller's verdict
  2. check read one validation's status
  3. invalidate mark every dependent validation stale, and return the count
  4. list the objects, optionally filtered by status
  5. statistics the counts
Consumed by
  • the approve step, which reads a validation's status
  • the audit hook, which writes the outcome evidence
  • the fs/observed listener, which invalidates

Rule The service records the caller's verdict and never invents one, and its sequence is its own counter rather than a wall clock.

Rule

A stale object is never guessed back to fresh: a revalidation is a new object that supersedes the old one.
