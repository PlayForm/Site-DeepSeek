Documentation/Design/Dissection-Design.md

The session is `c3b6f26c-81f6-4fbf-8feb-bf6697bb5fb4`, a delegated agent on the `@cf/deepseek-ai/deepseek-v4.1-flash-1017` route at `max`. It took the study sheet at `/manual/` (`Site/Source/pages/_Manual.astro` and `Site/Source/Stylesheet/Manual.scss`), which already carried every fact, and gave it UI fidelity by reading the Corca corpus as text and the overtrue registry as source, then editing the stylesheet in small slices with a compile between each.

The brief counted 216 tool calls and 190 steps. The decompressed log holds 217 `tool/call` events, 217 `tool/result` events, 191 steps, and 3 turns; the 217th call is the closing `send_message` (call 217) and its step, so the brief's snapshot may simply predate it. This dissection classifies all 217.

How this was reconstructed

I decompressed the log with `zstd -dc` and parsed the JSONL into four streams: `tool/call` (the tool name and the JSON `arguments`), `tool/result` (the text the agent saw), `assistant/message` (the visible text and the `reasoning` blocks), and the turn and step boundaries. I read the call digest end to end, the reasoning for every step that carried a decision, and the four large planning blocks (steps 17, 29, 37, 47) in trimmed form, cross-checked against the calls they produced. Every clause in the table below comes from a call's arguments or from its result. The `Pass-Log.md` was read only afterwards, to compare the agent's own account with the record; where the two differ, the record wins and the difference is noted.

2. The phases

| Phase | Calls | Count | What it did |
| --- | --- | --- | --- |
| A. The audit | 1-4, 17-20, 46 | 9 | Oriented, read the page and the stylesheet whole, read the token layer and the material mixins, inventoried the components, checked the git state of the target. |
| B. The corpus read | 5-16, 21-22, 47 | 15 | Listed the Corca shelf, read seven specimens and six curated documents and the compositions, then the Flywheel sheets and the overtrue inventory. |
| C. The specimen study | 23-45, 48-64 | 40 | Sized and read the overtrue compositions, read the remaining specimens and the contracts, read the site's own components and the formatter config. |
| D. The first band | 65-73 | 9 | Wrote the log's thirteen exploration entries, rewrote the whole page and the whole stylesheet in two writes, compiled once, inspected the compiled CSS. |
| E. The write loop | 74-141 | 68 | Read the page back after the formatter, recovered the original from the git index, diffed the facts, then edited band by band with a compile between. |
| F. The verification | 142-149 | 8 | Ran the closing check set, counted the repeated elements, checked the index state, fixed the lane label, reported. |

The phases are not disjoint in time. The verification is woven through the write loop as one compile per one or two edits, and the phase-F checks are the same checks run once more over the finished file. The first band was never built on its own: the agent wrote the whole page and the whole stylesheet in two calls, so the band-by-band discipline begins only in phase E, as a correction of that first move.

### Phase A: the audit (calls 1-4, 17-20, 46)

It read the target whole before anything else (calls 3 and 4, 715 and 1064 lines), then the token layer and the material mixins (17 and 18), then the component inventory and the alias config (19 and 20), then the git state of the two files (46). The audit's facts were assembled in the reasoning at step 37 and written into the log only at call 129, after the code existed. That is a finding about the record, not a defect of the pass: the audit was real, but the log's audit entry is a reconstruction written from the finished page, not a contemporaneous note.

### Phase B: the corpus read (calls 5-16, 21-22, 47)

Fifteen calls, all reads of text. It read the seven specimens and the six curated documents, the compositions, the Flywheel sheets, and the registry inventory. No image was opened; every specimen was read as markup and CSS. The output of this phase is the mechanics list that the reasoning names at step 17: the paint-order band, the lane's percentage track, the radio tabs, the gutter, the current-row marker, the lamp, the spec strip, the ruled spine, the display pair, the disclosure, the copy island.

### Phase C: the specimen study (calls 23-45, 48-64)

The largest reading phase, 40 calls. It sized the overtrue files before reading (23), read the compositions the brief named, read the site's own components (Line, Lane, SessionRecord, Flow, CopyButton, Base), read the contracts' state model, and read the formatter config. The decisive find was the site's own `Flow` component: its `why` disclosure, 40px index, and 2px kind edge became the decision spine's grammar (calls 59-61), which is why rule 8 exists.

### Phase D: the first band (calls 65-73)

Nine calls. It wrote the log's thirteen exploration entries before touching the page (65), then the page (66, 47,916 characters), then the stylesheet (68, 45,993 characters), then compiled (69), then inspected the compiled CSS (70-73). The "first band" is inside calls 66 and 68; no band was built alone. The phase's real output is 94 KB of source and one compile, and its real cost is the 75-call correction tail that phases E and F exist to pay.

### Phase E: the write loop (calls 74-141)

Sixty-eight calls. It read the page back after the formatter (74-78, 93-97), recovered the original from the git index (80-84), diffed the facts (85, 90-92, 133), and ran ten band groups (86-147; the last two cycles are counted in phase F because they double as the closing checks). The loop proper is described in section 3. Its shape is the point: after the big write, the agent never re-read a whole file again; it grepped, read a slice, edited one block, compiled, and grepped the next selector.

### Phase F: the verification (calls 142-149)

Eight calls. The closing check set (142: compile, markup balance, one `h1`, no `{" "}`, ASCII), the diff stat and line counts (143), the index state (144), the last design fix (146: the lane label at 10px), the element counts (148), and the report to the parent (149). The verification is not a separate activity in this pass; it is the loop's fifth move run over the whole file one last time.

### Phase G: the follow-up (calls 150-217)

Sixty-eight calls. It read the user's live page and the plugin's real ledger (150-151), read the session data model (152-173), tried and failed to ask a scope question (154), parameterized the session island with a `Data` prop and a `Session` default (169-190), authored the three-record activation run (186), fixed the axis and the title (198-206), appended Step 26 and extended rule 8 in the log (210-214), and verified against the running dev server (193-197, 207, 215-216). The follow-up is a different kind of work from the pass: it is data plumbing, not design, and it is the only part of the record where the agent reads a rendered page.

3. The write loop

This is the mechanic that made the page good, and it did not exist at the start. The agent's first move was two writes of 47,916 and 45,993 characters (calls 66 and 68) and one compile (69). The loop begins only after that, when the agent has to repair, verify, and refine what the two writes made. Its unit is one band.

### The cycle

Each cycle is five moves, in this order:

1. **Locate.** A `grep -n` on the source for the selector or attribute the band owns. The grep is chosen to return every hit, including the base rule and its media override: call 102 greps `&__band-head|&__band-index|&__band-body|&__band-label|&__band-row` and gets six lines, 318 to 349 and 2026. Call 118 greps `data-band="pair"` and gets both pair bands, 923 and 1183.

2. **Read the slice.** A `read` with `offset` and `limit` around the hit, never the whole file. The slice is 4 to 6 lines when the change is an attribute (calls 119, 135, 137, 140), 30 to 60 lines when the change is a block (calls 103, 105, 112, 87). In the loop proper, 13 slice reads for 17 edits, median slice about 40 lines.

3. **Edit one block.** One `edit` call, one band, one change. When the band needs two places (the desktop rule and the 760 override, the press and the reduced-motion guard), the agent edits them as two calls in the same cycle (104 and 106; 114 and 116).

4. **Compile.** One `sass` compile to `/tmp/manual.css`, with the exit code printed. The agent compiled 5 times inside the loop for 17 edits, roughly once every three edits, and 8 times in turn 1 in total.

5. **Grep the emitted selector.** After the compile, a grep on the compiled CSS to prove the rule survived the nesting and the `@for`: call 107 greps `sheet__band-head|sheet__band-body|sheet__band-label`, call 110 reads the compiled highlight, call 117 greps `sheet__decision-summary:active`. This is the check that catches a nested rule that compiled to the wrong selector.

Then the next grep. The next selector is never found from memory or by re-reading the file; it is found by grepping the source for the thing the band owns.

### The formatter is a co-author

The `write` and `edit` tools reformat the file after the write. The agent discovered this at step 53, when the page it wrote as 1300 lines came back as 1370 with every attribute broken across lines. Two consequences run through the loop:

- The formatter broke `(Overpass, StepBatch)` into `( Overpass, StepBatch)` by wrapping after the open paren. The agent fixed it by moving the parens inside the `<code>` spans (calls 88 and 89), which is the one edit in the loop that changes the rendered text on purpose.

- The formatter changes the file between the read and the edit. Call 98 failed with "file changed since it was read"; the recovery was a fresh `read` of ten lines (99) and the same edit again (100). After that, every edit cycle begins with a read of the slice it is about to touch.

### The fact checks inside the loop

The loop is not only visual. Twice the agent stopped the edits to prove the facts survived:

- The word diff (call 85) compared the visible text of the staged original (`git show :path`, 715 lines) with the new page: 957 words against 1184. The eight reported entries were five deletions of condition strings that moved from the summary into the disclosure, plus three replace entries that were word-alignment artifacts around those moves. Call 90 re-ran it after the paren fix: 1180 words, eight entries, and the greps at 91-92 proved every moved string was present.

- The sentence check (call 133) was too coarse, because the inserted UI words break the sentence boundaries; it reported 15 false misses and the agent fell back to the word diff.

### What the loop implies

The loop is cheap per cycle and expensive to enter. A cycle costs about 5 calls (grep, read, edit, compile, grep) and one to two minutes; the whole loop of ten bands cost 62 calls and about 12 minutes. The expensive part is the 75-call entry (calls 74 to 85 plus the read-backs), which exists only because the two big writes came first. If the first band had been written, compiled, and checked before the second, the formatter, the paren break, the `&nbsp;` question, and the missing copy import would have surfaced in the first ten calls instead of the sixtieth.

4. The turns

### Turn 1: the design pass (steps 1-127, calls 1-149, 29.4 minutes)

Asked: read the visual corpora widely, keep the bands and the facts, and give every interactive element its states, its interactions, the micro-mechanics, the detail fidelity, and guarded motion; write `Pass-Log.md` as a second deliverable with a `Read/Took/Decided/Built` entry per decision and a closing set of five to ten learned rules; obey the binding rules (site tokens only, no `{" "}`, `&nbsp;` at every boundary, no `.mjs`, one `h1`, ASCII, no fact or band changes, edit tools only).

Decided: read the corpus before touching the page, write the log's exploration entries first, then rewrite the page and the stylesheet whole, then verify and correct in slices. The agent chose the big write because the page was 715 lines and the stylesheet 1064, and it judged a full rewrite cheaper than 20 band edits.

Where it changed course:

- The formatter discovery (steps 53-57). The page came back reformatted, the `&nbsp;` boundaries sat at line ends, and the agent spent four calls comparing the pattern with `harness.astro` before deciding the site's own precedent was acceptable. It changed course only for the parens, which it fixed in the source.

- The original's location (calls 80-84). The agent assumed the page was committed in the parent repo; it was not, and `Site` was its own repo with the page staged, not committed. The original came from `git show :path`.

- The band head (calls 102-107). Reading the compiled CSS showed the index indenting the machine under it; the agent moved the index to the right of the label line and then had to fix the 760 override it had written an hour earlier.

- The cross-highlight (call 109). The hover rule was stepping the live node's accent name to ink, which erased the one meaning the accent carries on the canvas; the fix excludes the live node.

- The state set (step 88). The brief asked for "every state" on every interactive element; the agent decided a reveal target has no selected state and a reading surface has no press, declared the disabled mode without an instance, and wrote the reasoning into the log.

- The accent budget (calls 123-125). The log said four meanings; the stylesheet had five. The agent corrected the log to five rather than the stylesheet to four, because the fifth (the proof plate's copy control) was a real meaning.

### Turn 2: the permission note (1 step, 0 calls, 0.3 minutes)

Asked: "can also use the raw-write tool if you're encountering errors with the built in ones."

Decided: nothing needed it. The agent replied that the write and edit calls went through, apart from the one stale read on `Manual.scss`, which it had resolved by re-reading. It did not start new work and did not use `raw-write`. The reply also named the formatter as the reason the `&nbsp;` boundaries sit at line ends.

### Turn 3: the follow-up (steps 1-63, calls 150-217, 11.9 minutes)

Asked: "the `http://localhost:9999/manual/#show`, needs less content, not less simplicity and it needs to showcase a run (or a turn) where the plugin was activated." Two interjections arrived mid-turn: "this is the import `SessionView` from `@Component/SessionView.tsx`; component I'm talking about" and "but it's being shown. (as it should, just needs to be parameterized)."

Decided, first: read the live page and the plugin's real ledger, then cut content and condense the payload strip. The agent read 225 lines of the payload block (call 155) in preparation for the cut, and tried to ask the user which content to remove (call 154); the question failed because the agent is owned by a live parent, so it decided to act on the least destructive reading and report the ambiguity.

Where it changed course:

- The interjections redirected the plan. The SessionView is the component; it is shown; it needs parameterization. The agent abandoned the content cut, kept every band, and made the run the thing that changes (steps 5-8).

- The data model (calls 158-173). The helpers read the module arrays directly, so the agent added a `SessionData` interface, a `Session` default, and an optional `Data` argument on six helpers, then passed `Data?` through the four child components. The trace and package pages keep the default.

- The activation file (calls 183-186). The agent assumed `Content/Activation.ts` was free; it existed and holds the activation-line content. The write failed, the agent read the file, and it created `Content/Manual.ts` instead.

- The axis (calls 198-203). The rendered lane rounded a 1.4s run to three identical "1s" ticks, so the agent re-authored the durations to 1.2s, 6s, and 0.8s for an 0-8s axis.

- The title (calls 204-206). "The whole run" was no longer true of a one-turn run, so the band title became "One turn, the hook brought out".

The ratios that matter for scheduling:

- **Reads to writes.** 62 reads and 45 bash calls that carry a grep against 31 successful edits and 7 successful writes. The pass is a reading pass that occasionally writes; the reading is not overhead, it is the work.

- **Edits per band.** 1.7 on average, 1 at the median, 3 at most. A band is one block, not a campaign.

- **Compiles per edit.** 0.44 across turn 1 (8 compiles, 18 edit calls), 0.29 inside the loop. The compile is the cheapest arbiter available when the build is forbidden: one call, under two seconds, and it catches every Sass error and every nested selector that compiles to the wrong shape.

- **The entry cost.** 64 calls before the first write, 87 before the first page edit. Most of that is the corpus and the specimen study, which a second page in the same house does not need to repeat.

- **The correction tail.** The two big writes took 2 calls; the correction and verification took 75 (74-148). The loop is not slower than the big write; it is the only part that produced a correct page.

### Scheduling the same pass on another page

Budget, for a page of the same size (about 1,300 lines of markup and 2,000 of stylesheet) in the same house:

1. **Audit and corpus, 20 to 30 calls.** Reuse the notes from this pass: the mechanics list, the corpus map, and the site's own component inventory are already written down. Read the target page and stylesheet whole, the token layer, and the site's own components; skip the shelf.

2. **First band, 3 to 5 calls.** Write one band, compile it, grep the emitted selector, and read it back. Do not write the page.

3. **The loop, 50 to 60 calls.** Eight to ten bands at 5 calls each: grep, slice read, edit (one or two), compile, emitted-selector grep. Expect 1.7 edits per band and one compile per two edits.

4. **The log, 3 to 6 calls.** One entry per band as you go, not at the end.

5. **Verification, 6 to 10 calls.** Compile, parser balance, word diff against the index original, ASCII scan, one `h1`, no `{" "}`, and a read of the running page if one exists.

6. **Total: 80 to 110 calls, 20 to 25 minutes** at the observed 5 calls per minute, against the 217 calls and 42 minutes this pass took. The saving comes from two places: the corpus is not re-read, and the correction tail does not exist because the first band is compiled before the second is written.

The three failure modes to schedule against: the big write (it converts 2 calls into 75), the formatter (it invalidates every read and rewrites every boundary), and the assumption about a file or a tool (one check settles it; skip the check and pay for a retry).

7. What the log does not show

- **The page itself.** No screenshot, no render, and no browser in turn 1. Every visual claim in the pass rests on the compiled CSS, the reasoning, and the agent's reading of the markup. The follow-up reads the user's running server, but only as HTML text through `curl` and a parser; nobody looked at a picture of the page.

- **A type check.** The compile is Sass only. The follow-up's TypeScript changes are checked by the dev server rendering a 200, not by `tsc`; a type error that does not throw at render time would survive.

- **The private reasoning.** The log stores the visible text and the reasoning blocks, not the model's internal deliberation. The reasoning blocks are the agent's own narration, and the large planning blocks (steps 17, 29, 37, 47) are where the design was actually decided.

- **A commit.** Nothing was committed in either repo. The Site repo's index holds the agent's writes because the tooling stages them; the working tree is the deliverable.

- **The log's own count.** The report at call 149 says "25 steps"; Step 26 was appended at call 212. The final log has 26 steps and 10 learned rules.

- **The measurements that came from taste.** The 96px rail, the 72px mark plate, the 40px band index, the 10px micro scale: the log gives reasons for some, and the reasoning gives more, but the exact numbers are not derivable from the corpus alone. A later agent should copy the numbers from the stylesheet, not re-invent them.

- **The Pass-Log's rules are not independently validated.** The same agent that did the work wrote them. This dissection re-derives each one from the calls, and the skill gives every rule the call numbers that paid for it, so the next agent can check the evidence instead of trusting the rule.
