PLUGIN DETAIL FLAVOR: FILE v0.1.0 TOOL + TWO OVERPASS ARMS

plugin-dsh-normalize-file

Plugin @ DSH @ Normalize @ File • The DeepSeek Harness Plugin Family for PlayForm. The file-content normalizer - a DeepSeek Harness plugin that registers the normalize family's normalize-file TOOL: the read count write pipeline over files ALREADY on disk, beyond the tool layer.

One agent-chosen file per call: the target's content is read, the family's SIX transforms are applied with a per-character count, and ONLY when N > 0 is the rewritten content written back through the factory's ONE shared write executor.

N = 0 writes NOTHING - the no-op no-write rule.

The family's tool flavor: no llm/stream , no fs/observed - the six-fold pass runs on an explicit agent call, or on the two opt-in overpass arms whose scopes default off.

This bundle's own tool calls are name-exempt in the stream gate beside edit and raw-write - its arguments carry a FILE PATH, and a normalized dash inside a filename would corrupt the target.

The Problem

WHY THE FILE TOOL EXISTS

Files that never passed through a write tool being invisible to every normalization layer DSH has - raw-write's normalize: true an explicit per-call opt-in for NEW writes, the six stream flavors only rewriting model output, never touching disk - a pre-existing file keeping every typographic character it was born with, exactly the characters that break parsers, shells, diffs and byte-exact edit matches downstream.

Files that never passed through a write tool are invisible

They are invisible to EVERY normalization layer DSH has: raw-write's normalize: true is an explicit per-call opt-in for NEW writes, and the six stream flavors ONLY rewrite model output - they NEVER touch disk.

Left unnormalized, a pre-existing file keeps EVERY typographic dash, curly quote, ellipsis, unicode space, zero-width character and full-width character it was born with - exactly the characters that break parsers, shells, diffs and byte-exact edit matches downstream.

Files rewritten behind the agent only at the price of the edit tool's old_string contract - the agent reading bytes X, a background rewriter silently changing them to X', the next edit failing or half-matching - the cautionary precedent of normalize-tabs.sh, a repair hook for a repair hook, existing to repair the damage after-the-fact rewriting caused.

The fix cannot be another silent rewriter

But the fix cannot be another silent rewriter.

The tool is the answer: explicit, visible, discoverable, and idle until the agent calls it.

Every arm gated independently - and all volatile

The scopes object gates EVERY arm of the plugin-dsh-normalize-file hook independently - conversation, reasoning, toolInput, toolResults, files, batch - with the defaults exactly the pre-scopes behavior.

The whole object is volatile: one leaf change commits one loader/volatile-update dispatch whose whole object the State's refresh listener re-reads - live, silent, no remount, no new activation line (a flip lands WITHOUT remounting).

The tool-input arm: effective tool-input normalization is normalizeToolArguments || scopes.toolInput - the field is kept and OR-ed in, so EVERY existing profile keeps working.

It is the ONLY execution-critical arm, and it carries the per-call escape hatch: a call whose arguments open with the {"__normalize":false} FIRST-key marker passes through unnormalized, the marker entry stripped (the executed call carries no unknown key) - the "leave that search alone" control for a deliberate search for an irregular character.

The marker must be the first key: a first delta shorter than the marker is invisible to the probe and the call normalizes normally.

The normalize-file call itself is a structural exemption: its arguments carry a file path - a normalized dash inside a filename would corrupt the target.

Two more structural exemptions are NEVER rewritten: the edit call (its old_string must match the real file bytes) and the raw-write call (it owns its content normalization through its explicit normalize parameter).

And the overpass invisibility contract: the tool-results arm replaces the bytes PRE-COMMIT - the waterfall settles before the result is appended to the durable log - so the model ONLY ever sees the normalized output and NEVER notices the replacement; the exemption list plus the <<<CCR: marker guard define what passes untouched.

That is the write-path counterpart of the governance trio's never-notify precedent: the result is built from the author's own content, and the observation-policy's version record is refreshed by the re-emitted fs/observed.

In Action

ONE CALL, ONE FILE, ONE COUNT

Before - the file as it sits on disk

Every em dash (U+2014) becoming the ASCII hyphen-minus, the curly quotes straight ones, the ellipsis three periods - five characters replaced, so N = 5 and the write happens; the result carrying the outcome, the diff card showing the before/after in the same turn, the ledger getting the count line.

The counted write

EVERY em dash (U+2014) becomes the ASCII hyphen-minus, the curly quotes become straight ones, the ellipsis becomes three periods; five characters replaced, so N = 5 and the write happens.

The result carries the outcome and the diff card shows the before/after in the same turn; the ledger gets the count line shown below.

A file with nothing to replace being a no-op: changed: false, the file staying byte-identical, no write, no count line, no journal record - a missing, binary or undecodable target being an error result with no write - and re-reading before editing, because the file's bytes change under you.

The no-op and the error cases

A file with nothing to replace is a no-op: changed: false, the file stays byte-identical, no write, no count line, no journal record.

A missing, binary or undecodable target is an error result with no write.

Because the file's bytes change under you, re-read before editing - the edit tool's old_string must match the new content.

The schema shape is identical in every family hook, so one grouped override in the profile patch turns the whole family off in one edit:

  config:
      scopes:
          conversation: false
          reasoning: false
          toolInput: false
          toolResults: false
          files: false
          batch: false
